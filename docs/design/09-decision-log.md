# 9. Decision log

Each decision records the context, the options that were really considered, what was chosen and why, what it costs, and what evidence would change it. Decisions were challenged against what we measured in the simulator; where the first plan did not survive, it was changed and the change is listed in 9.2.

Status values: **Accepted** (in force), **Revised** (replaced the first plan), **Proposed** (to be confirmed when built).

## 9.1 Decisions

### ADR-01 Backend language and framework: Python with FastAPI. Accepted

| | |
|---|---|
| Context | A backend that polls, forecasts, optimises and serves an API, with a one-week deadline. The brief allowed Python or Spring Boot. |
| Options | **Python and FastAPI**; Spring Boot (Java); Node and Express |
| Decision | Python 3.12, FastAPI, httpx, Pydantic v2 |
| Why | The intelligence layer is numerical (NumPy, SciPy), and the HiGHS solver is one function call away. Pydantic gives strict validation for the simulator's payloads. FastAPI gives typed endpoints and generated API docs. One language across ingest, intelligence, benchmark and chaos scripts means the benchmark imports the same code as the live system. |
| Cost | Python is slower than the JVM per request; irrelevant at this scale (cache-served reads, one poller). Threading and the GIL are avoided by using `asyncio` for I/O. |
| Revisit if | The API must serve far more than a few dozen clients, or the team has no Python experience. |

### ADR-02 One poller and an immutable snapshot. Accepted

| | |
|---|---|
| Context | The simulator handles about 60 to 76 requests per second and reset a connection at 50 concurrent clients. Many consumers (UI, forecaster, allocator, benchmark) need the world. |
| Options | **One poller feeding an immutable snapshot**; each consumer reads the simulator on demand; each consumer polls on its own |
| Decision | A single poller builds a frozen `WorldSnapshot` once per refresh and swaps it atomically. Everyone else reads the snapshot. |
| Why | Simulator load becomes independent of the number of viewers. All consumers see one consistent world, so the forecast and the proposals refer to the same tick. A failed read cannot corrupt state because it never replaces a good snapshot. A tick read before and after each world read removes torn reads. |
| Cost | Data is at most one cycle old (0.5 s plus read time), which is up to about two ticks at 4.6 ticks per second. Shown as age on every value. |
| Revisit if | Sub-tick latency becomes a requirement. |

### ADR-03 State: in-memory snapshot plus SQLite in WAL mode. Accepted

| | |
|---|---|
| Context | We must keep an audit trail, idempotency keys and proposals across restarts, and demand history for the forecaster. |
| Options | **SQLite**; PostgreSQL; memory only; Redis |
| Decision | The world lives in memory; SQLite holds history, proposals, ledger and audit |
| Why | Memory only cannot give exactly-once execution after a crash: the idempotency key must be on disk before the request is sent. PostgreSQL adds a service, a connection pool and start-up ordering for a single writer. SQLite in WAL mode is durable, has no operations, and is a single file on a volume. Most data is reconstructable (part 3.4), so the durable part is small. |
| Cost | One writer process; no horizontal scaling. Acceptable: one backend instance is the design. |
| Revisit if | More than one backend instance is needed. |

### ADR-04 Poll REST for truth; use the stream only as a hint. Accepted

| | |
|---|---|
| Context | The simulator offers server-sent events, and the guide encourages them. Measured: the stream sends a tick event but nothing for departure, arrival, failure or station stock; a slow client is dropped silently with the connection left open; a fault can reject new connections. |
| Options | **Poll, with the stream as an accelerator**; stream-driven with REST for catch-up; stream only |
| Decision | Polling is primary and sufficient. A stream listener, when built, only triggers an earlier refresh, and a watchdog judges liveness by tick progress. |
| Why | A design that does not depend on the stream has no stream failure to handle: `stream_disconnect` and silent drops cost us nothing but latency. It is better to remove a failure mode than to handle it. The stream cannot be the source of truth because most state changes never appear on it. |
| Cost | Up to one poll interval of extra latency; a steady trickle of tick reads while idle (one request per 0.5 s). |
| Revisit if | Measured polling load or latency is a problem; the stream would then be promoted, with REST reconciliation kept. |

### ADR-05 Forecaster: a structural model learned online. Revised

| | |
|---|---|
| Context | Demand is generated by a known structure (part 6.1), the data starts empty, and the first stockout is 65 ticks away. |
| Options | **Structural model with learned hour bins, a profile prior and an adaptive multiplier**; ARIMA or Prophet; gradient boosting (LightGBM); a neural network; seasonal-naive only |
| Decision | `level(s,f,hour) x spike multiplier x adaptive factor`, with a Bayesian prior for unseen bins, quantiles on cumulative demand, seasonal-naive as the fallback |
| Why | The generator is two-level step functions with independent noise, so a few hours of data identify it; generic models need days and cannot use the events feed. The event list explains spikes before they appear in the data. The noise floor is known (half the noise amplitude), so accuracy can be judged honestly. Boosting and neural models add dependencies and an opaque failure mode for no accuracy gain on this signal. |
| Cost | The model is fitted to this simulator's structure; the README says so. Pooling and the prior come from reading the simulator's source. It transfers to real data only after refitting; the learning is data-driven, so a differently configured simulator is learned rather than assumed. |
| Revisit if | Residuals show structure the model misses; then a gradient-boosted challenger on the residuals is the first step. |

### ADR-06 Allocation: greedy first, then a rolling-horizon linear programme. Revised

| | |
|---|---|
| Context | Shipments from a depot compete for one dispatch capacity per tick, route maxima, depot stock and station headroom. The aim is the simulator's own score: litres served. |
| Options | Rules only; **greedy by urgency**; mixed-integer programme (OR-Tools); **linear programme (SciPy HiGHS)**; reinforcement learning |
| Decision | Greedy comes first and is kept as fallback and benchmark policy. The main policy is an LP over 48 ticks, committing only the first tick, re-solved at every snapshot. |
| Why | All decision variables are continuous litres and every constraint is linear, so the problem is an LP, which a MIP solver would solve with extra machinery for no gain. SciPy is already a dependency of the numerical code; OR-Tools is a large extra one. Rolling the horizon makes the plan correct itself as events change the world. Greedy decides one station at a time and can burn a depot's dispatch capacity on a less critical station; the LP decides all together, which is exactly the contention the simulator creates. The benchmark decides whether the LP earns its place. RL is out of scope: it is opaque, needs training runs, and would have to beat these on the replay. |
| Cost | Rounding after solving can lose a little optimality; minimum-lot rules are not modelled in the LP. |
| Revisit if | A minimum shipment size must be optimised (then add integer variables), or the benchmark shows no gain over greedy (then keep greedy as default and report it). |

### ADR-07 Workflow: propose, approve, execute; approval is an upper bound. Revised

| | |
|---|---|
| Context | The brief wants recommendations, and an operator console implies a human decision. But a 30 second approval is about 140 ticks at 4.6 ticks per second, so a proposal is stale before it is approved. |
| Options | Auto-execute only; propose and approve with a **hard expiry** (the first plan); **propose and approve, approval bounding the quantity, re-validated at execution**; manual entry only |
| Decision | Approval authorises "up to this quantity on this route for this need". At execution the proposal is re-validated on a fresh snapshot and the quantity may only shrink. An optional autopilot mode executes within guard limits, for benchmarks and for hands-off demos. Expiry is 40 ticks. |
| Why | A hard expiry short enough to be safe would expire every proposal before a human could act. Re-validation, not expiry, protects correctness, so expiry can be long. Approvals that can only shrink are safe: the operator never causes more than they saw. Autopilot is needed anyway for the benchmark, so it costs little and makes the platform usable without a person. |
| Cost | The executed quantity may differ from the approved one, so the UI must show both. |
| Revisit if | Evaluators prefer to pause the simulation while deciding; the UI offers a pause control for that (ADR-16) and the design holds either way. |

### ADR-08 Time is measured in ticks; tick length is read at runtime. Accepted

| | |
|---|---|
| Context | The published image defaults to 15-minute ticks at speed 8; the guide's compose file overrides them to 8 minutes and speed 15. A reset restores 15 minutes. |
| Options | Hardcode 15; **read `tick_minutes` from `/v1/instance` on every snapshot** |
| Decision | Everything inside is in ticks; hours are derived from the snapshot's own `tick_minutes` |
| Why | We cannot know which setting the evaluators run. The cost of reading is zero. |
| Cost | Demand per tick is hardcoded for 15-minute ticks in the simulator (`daily / 96`), so at 8 minutes a tick holds less time than demand assumes; our model learns per-tick demand from data, so it is unaffected. |
| Revisit if | Never needs revisiting, but both settings are in the test matrix. |

### ADR-09 World epochs and reset detection. New

| | |
|---|---|
| Context | An evaluator can reset the simulator at any time; the tick goes backwards. State survives a restart, so a restart does not reset. |
| Options | Ignore; **detect and start a new epoch**; require a manual reset of our system |
| Decision | A tick lower than the last published tick, a changed scenario, seed, instance or tick length, or running counters (allocation count, served litres) that went backwards, starts a new epoch: caches and open proposals are discarded, history is reloaded, and everything persisted is keyed by epoch |
| Why | Without it, a reset mid-demo leaves stale proposals on screen and a forecaster trained on another world. It is cheap, testable, and a likely evaluator action. |
| Cost | A little bookkeeping in every table. A reset followed by a run past the old tick inside one poll interval, with nothing allocated, goes unseen; seeded demand makes the stored history still valid, so the harm is limited to our own state (Figure 4.9 note). |
| Revisit if | The executor exists: add missing-allocation-of-ours as a signal. |

### ADR-10 Frontend: Next.js; the browser polls first, streaming later. Accepted

| | |
|---|---|
| Context | A dashboard with a grid, an inbox and approval cards, served by Compose. |
| Options | **Next.js with TypeScript and Tailwind**; a Vite single-page app; server-rendered templates |
| Decision | Next.js, with the browser polling `/api/snapshot` and `/api/proposals` every second. Server-sent events from our backend are an upgrade. |
| Why | The user asked for Next.js, and it is production-shaped. Polling a memory-served endpoint with an `ETag` costs almost nothing and cannot get stuck the way a stream can. The scarce resource is build time, not browser requests. |
| Cost | Up to one second of display lag. |
| Revisit if | One second feels slow in the demo; then add `/api/stream`. |

### ADR-11 Observability: metrics and logs first, Grafana as a stretch. Revised

| | |
|---|---|
| Context | Observability and performance are 10% of the score. The first plan made Grafana dashboards, burn-rate alerts and a full set of panels a day-four must-have. |
| Options | Full Prometheus, Grafana and alerting; **instrument first, add dashboards after**; OpenTelemetry tracing |
| Decision | Build the `/metrics` endpoint and JSON logs early, because the drills, the SLOs and the load test all read them. Grafana, burn-rate pairs and tracing come after, in that order. |
| Why | Metrics are needed to verify resilience claims; a pretty dashboard is not. Bounded labels (part 8.5) keep series count flat. Tracing adds nothing for one process. |
| Cost | Fewer polished panels at the first demo. |
| Revisit if | Time remains after the core path works. |

### ADR-12 Packaging: Docker Compose, ports in `.env`, a `bench` profile. Accepted

| | |
|---|---|
| Context | Evaluators must start the system easily; benchmarks must not disturb the demo world. |
| Options | **Compose**; Kubernetes; bare scripts |
| Decision | One Compose file; every host port configurable; the second simulator is behind a `bench` profile |
| Why | Compose is the stated deployment target and is one command. The bench profile keeps the demo world untouched. Kubernetes is far more than a single-host demo needs. |
| Cost | The bench simulator is a second container to start. |
| Revisit if | Never for this scope. |

### ADR-13 Retries: per request, budgeted, with jitter. Revised

| | |
|---|---|
| Context | A world read is 10 requests and any failure fails the read. The error-rate fault fails 24% of requests independently (measured). |
| Options | No retries; retry the whole refresh; **retry each request** |
| Decision | Two retries per request with full jitter, a rolling budget of 40% for reads, no retries for 404, 409 or 422, and a separate rule for writes (ADR-14). The first plan said 3 attempts and a 10% budget. |
| Why | The arithmetic in part 8.1.1: with no retries a refresh fails 94% of the time at the default fault; with two retries per request it fails 15%. Retrying the whole refresh wastes the nine requests that succeeded. The expected cost is 31% extra requests, so a 10% budget would starve the retries exactly when they are needed; 40% still stops a storm. |
| Cost | Up to 1.4 times the request rate during a fault. Within the load budget because the cadence is capped. |
| Revisit if | The chaos drill D2 shows different behaviour. |

### ADR-14 Writes are idempotent and ledger-first. Accepted

| | |
|---|---|
| Context | A POST that times out may have succeeded. A crash between deciding and sending must not lose or duplicate an allocation. |
| Options | Send first and record after; **record the key and body, then send, and retry the identical pair**; avoid retrying writes |
| Decision | The line, its key `fw-p{proposal}-l{line}` and the quantity are written to SQLite before the request; retries send the stored pair; an unknown outcome is reconciled by searching allocations for the key |
| Why | The simulator makes this exactly-once: the same key and body returns the existing allocation, and a validation 409 does not consume the key (both measured). Not retrying writes would turn every transient fault into a lost action. |
| Cost | A disk write before each POST. |
| Revisit if | Never needs revisiting. |

### ADR-15 The benchmark uses the live decision code on a second simulator. Accepted

| | |
|---|---|
| Context | The headline claim is "better than doing nothing"; a claim needs a fair, repeatable test. |
| Options | Benchmark a re-implementation in a notebook; **run the real code against a second simulator**; compare only on the demo world |
| Decision | `bench/` imports the same client, intelligence and decision modules and runs them against a simulator on port 8001, reset for every policy |
| Why | The simulator is deterministic (identical hashes across runs), so each policy faces the same world. Importing the live code means the benchmark measures what actually runs. A second container leaves the demo untouched. |
| Cost | A second simulator to start. Runs take real time: a 192-tick run is at least about 40 seconds at the measured 4.6 ticks per second, and stepping tick by tick is bounded by our own request time instead. |
| Revisit if | Never needs revisiting. |

### ADR-16 Security and control surface. Accepted

| | |
|---|---|
| Context | The simulator has no authentication. Our write and control endpoints could change the simulation. |
| Options | None; **a shared operator token for writes and controls, reads open**; full user accounts |
| Decision | `X-Operator-Token` is required to approve, reject, change autopilot, and use the demo controls that proxy the simulator's run, pause, step and reset. The browser never calls the simulator. |
| Why | Matches the risk: a demo environment with one role. The proxy keeps the one-way rule (the browser never touches the simulator) and lets the console offer run, pause and step, including pausing while a decision is made. |
| Cost | A secret in `.env`. |
| Revisit if | Real multi-user use is wanted. |

## 9.2 What changed from the first plan

| Topic | First plan | Now | Reason |
|---|---|---|---|
| Optimiser | Mixed-integer programme, OR-Tools or PuLP | Linear programme, SciPy HiGHS, with greedy fallback | No integer decisions exist; fewer dependencies; faster (ADR-06) |
| Approval | Proposal expires after a few ticks | Approval is an upper bound; re-validate; expiry 40 ticks | A 30 s approval is 140 ticks; expiry cannot protect correctness (ADR-07) |
| Stream | Central, with a watchdog | Optional hint; polling is primary | Removes a failure mode instead of handling it (ADR-04) |
| Retries | 3 attempts, 10% budget, read and write separate | 2 retries per request, 40% read budget | Measured 24% error rate and 10 requests per read (ADR-13) |
| Forecaster | Structural model with residual quantiles | Online-learned hour bins, profile prior, event multiplier, quantiles on cumulative demand | Demand structure verified; cold start; events explain spikes (ADR-05) |
| Observability | Grafana and burn-rate alerts by day four | Metrics and logs first; Grafana later | Metrics are what verify claims (ADR-11) |
| Browser feed | Server-sent events | Polling first | Cheaper and cannot stall (ADR-10) |
| World resets | Absent | Epochs and reset detection | Evaluators can reset at any time (ADR-09) |
| Autonomy | Human approval only | Manual by default plus autopilot | Needed for the benchmark; useful for demos (ADR-07) |
| First stockout | Cox's Bazar near tick 63 | Tongi diesel at tick 65 | Re-measured; the earlier note was wrong |
| `error_rate` | Open question | Measured: 23.9% independent | Closed by test; changed the retry design |
| Lead time | "transit + 1" | Arrival applied in processing tick `created + transit`, before demand; visible one step later | Read from the tick order in the source |
| Simulator load | Assumed fine | Budgeted: about 22 requests per second against 60 to 76 capacity | Calculation in part 4.1; to be confirmed |
